# Windows host readiness diagnostic for Gate 2B Experiment 00

This read-only diagnostic reports candidate Windows host facts for the disposable default-deny experiment. It does not build, stage, launch, monitor, or authorize anything. **Experiment 00 remains NO-GO; production execution remains disabled.** The separately reviewed [Experiment 00 authorization package](BUILDER_WINDOWS_GATE2B_EXP00_AUTHORIZATION.md) controls future build and runtime approvals.

`tools/mission-control/src/hostReadiness.ts` defines platform-neutral statuses (`READY`, `MISSING`, `UNVERIFIED`, `UNSUPPORTED`), report/check types, and a deterministic assessor for fixtures. `tools/mission-control/src/windowsHostReadiness.ts` collects local `os` values and stops Node `lstat` inspection at the volume root before following any ancestor whose native reparse status is unverified. Candidate paths remain fixed but most file presence checks therefore remain unverified. It does not read process events or filesystem contents and does not call a native executable, shell, controller CLI, or worker. It does not implement a Linux/macOS runner; a non-Windows host is reported as unsupported without filesystem inspection.

The pure assessor accepts raw facts so tests can cover missing, unsupported and contradictory cases without accessing the host. Such facts are explicitly unauthenticated. Extra caller fields such as `trusted`, `authorized`, or `cleanupComplete` are rejected as malformed; every report fixes `experiment00: 'NO_GO'`, `productionAuthorized: false`, and `executable: false`. The Windows adapter's `LOCAL_READ_ONLY_INSPECTION` label describes where metadata came from, not trusted enforcement or authorization. An exception, inaccessible path or unresolved evidence must not become `READY` for the affected control.

Before any future build, an independent reviewer still needs protected disposable staging and effective parent/child ACL evidence, source and executable hashes/file IDs, actual toolchain resolution, a reviewed continuous process observer with loss bounds, cleanup evidence, and explicit human **build/staging approval B**. **Runtime approval C** is separate and follows review of the build and observer evidence. Neither this diagnostic nor a `READY` availability row grants either approval. No default-deny setting, worker admission gate or production control is changed by these modules.

## Gate 2B security hardening (2026-10-23)

The pure assessor now requires exact own-data-property records (no unknown string/symbol keys, accessors, or unsupported prototypes), and dense ordinary arrays without overridden methods, accessor indices, sparse slots, or extra properties. Values are copied from property descriptors into fresh records and arrays before assessment. Contradictory root/ancestor paths are rejected as `MALFORMED_OR_CONTRADICTORY_FACTS`. Additional caller assertions such as `trusted`, `authorized`, or `cleanupComplete` are rejected, not silently accepted.

The Windows adapter uses a pinned `C:\Windows` candidate, never a caller-supplied `SystemRoot` as filesystem traversal authority. It does not inspect candidate tools or event logs beneath ancestors whose native reparse state is unknown. Node `lstat` can reveal some symbolic links but cannot establish all Windows reparse tags or protected file-handle identity. Accordingly the bounded adapter currently leaves candidate-file metadata `UNVERIFIED` and does not claim toolchain or process-observer availability until a separately reviewed native handle-based inspection provider exists. This is a deliberate reduction in diagnostic detail rather than an assertion that the files are missing.

These changes do not establish actual NTFS ACL protection, independent process event coverage, durable cleanup, trustworthy Windows filesystem identity, or any human authorization. Experiment 00 remains NO-GO and native/runtime work remains unauthorized.
