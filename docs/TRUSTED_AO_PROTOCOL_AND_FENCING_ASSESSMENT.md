## 2. Unverified AO capabilities

Repository documentation and code do not confirm any AO facility for: authenticated dispatch acceptance or rejection; persistent dispatch-ID lookup; exactly-once idempotency; durable queue retirement and cancellation; ordered STOP/fencing epochs; exact session generation checks; trusted grant verification and consumption at worker start; authoritative no-spawn evidence; or independently obtainable provider event history. CLI command availability, session listings, branch state, a Builder appearing, and an AO review verdict would not prove these semantics. This assessment did not inspect an AO installation, invoke AO, contact a daemon or worker, or inspect live state. Each capability needs a versioned provider specification, implementation evidence, and isolated conformance tests before any live design can rely on it.

## 3. Required provider protocol

The minimal conceptual exchange is `submit(dispatch envelope) -> verified acceptance | verified rejection | unknown`, `lookup(dispatchId) -> authoritative current record`, and `retire(scope, epoch, dispatchId?) -> durable fencing receipt`. These are **requirements**, not existing API names. A plain network success or client-generated receipt is insufficient.

1. **Immutable identity and payload.** The controller persists one immutable dispatch ID and operation key before submission. The envelope binds protocol version, repository and project, issue, branch/worktree identity, exact target ID and session generation, action, canonical payload digest and digest algorithm, grant ID, caller identity, expiry, and fencing epoch. The provider recomputes the digest over the actual executable bytes using an agreed canonical encoding; a digest alone cannot authorize a different payload. Reuse of an ID with different bytes or target is a permanent conflict.
2. **Verified acceptance and rejection.** The provider returns signed or otherwise independently authenticated, versioned receipts bound to dispatch ID, digest, target/session generation, grant, epoch, provider instance and durable sequence, decision, timestamp, and reason. Acceptance means the provider has durably recorded one candidate and applied admission checks; it does **not** mean a worker ran or that later STOP cannot fence it. Rejection means the provider durably recorded no executable instruction for that ID and will never later accept it. Receipt provenance, signature/key rotation, replay window, schema, clock bounds, and sequence must be verified outside caller-controlled fields. Unknown, malformed, contradictory, or unverifiable receipts remain uncertain.
3. **Idempotency and authoritative lookup.** Provider storage atomically maps dispatch ID to one digest, target, and outcome before acknowledgment. Repeated identical submissions return the same record without another queue entry or spawn; conflicting repeats reject. Lookup by exact dispatch ID must report accepted, rejected, executing, completed, retired, or unknown with authenticated history and a documented completeness/retention guarantee. A bare `not found` is not proof of no delivery unless the provider guarantees that a delayed original cannot subsequently appear and that the lookup covers every ingress path.
4. **Trusted execution authorization.** A provider-side gate verifies issuer provenance, authenticated actor, action/target/repository scope, expiry on a trusted clock, current grant revocation, single-use consumption, STOP/fencing epoch, and target/session generation **atomically at queue admission and immediately before spawn or any effect**. Queueing must not consume or bypass a later revocation. All possible AO instruction ingress and worker-start paths must use this gate; if one bypass exists, the guarantee fails.
5. **Durable retirement and fencing.** STOP/revocation increments a provider-enforced monotonic epoch (scoped to the relevant repository/project/target), durably retires older pending dispatches, and yields an authenticated barrier receipt. The provider checks the current epoch under the same ordering authority as queue dequeue and worker creation. Retirement must specify whether an already running worker is terminated or merely barred from new effects; both need separate evidence. Epoch rollback, stale worker snapshots, and replayed queue messages fail closed after restart.
6. **Crash recovery and independent audit.** Acceptance, rejection, execution-start, completion, retirement, epoch advance, and grant consumption survive provider restart, with causally ordered event IDs. An independent read path or append-only signed export supplies evidence separate from the controller's own JSONL. Reconciliation combines provider truth with the local B2 ledger; it never fabricates an outcome from local state or blindly replays uncertain work.

For the strong property “an old delayed instruction cannot spawn a new worker,” the provider must make the epoch check and worker creation an indivisible ordered decision against durable current fencing state. Checking at controller send time, queue insertion, or receipt issuance alone leaves a time-of-check/time-of-use gap. A STOP acknowledgment must certify the barrier has committed at every execution ingress, including reconnecting workers and restarted queue consumers. If this cannot be demonstrated, STOP is advisory and live assignment remains blocked.

## 4. Trust boundaries and component choice

| Component | Role and trust limit | Recommendation |
| --- | --- | --- |
| Narrow AO adapter protocol | Marshals versioned envelopes, authenticated receipts, lookup, and retirement; never treats CLI text/session discovery as authority. | Needed only after AO demonstrates these primitives. Keep `AoClient` observations separate from the new provider protocol. |
| Independent authorization gateway | Verifies trusted issuer and actor, scope, clock, revocation, one-use grant, and STOP. | Needed if AO cannot host this logic directly, but an external gateway alone is insufficient when AO accepts other instruction paths or starts queued work without rechecking its fence. The AO-side execution gate remains mandatory. |
| Durable dispatch ledger | Reuse B2 IDs, digest, quarantine, and controller lock. Extend evidence and recovery schema only after protocol semantics are proven. | Needed. Define file/directory durability, transactional evidence linkage, retention, and migration before transport. Never promote existing fixture evidence. |
| Trusted receipt verifier | Authenticates provider, validates bindings and sequence, rejects stale/conflicting records, and stores raw evidence reference separately. | Needed; receipt fields supplied by a caller or adapter name alone are untrusted. |
| AO-side execution gate | Controls every queue admission and worker start, with atomic grant, generation, and epoch checks. | Indispensable. No controller-only substitute meets the delayed-instruction guarantee. |
| Durable retirement/fencing authority | Orders STOP/revocation against queue and spawn, survives restart, and certifies barrier completion. | Indispensable. Must provide dispatch-specific and scope-wide retirement evidence. |

Controller state and audit are inside a local trust boundary; AO transport, queue, daemon, and workers are separate; an authorization issuer is a distinct authority. A receipt verifier must trust a pinned provider identity and authenticated channel/signature, not a response shape. The controller lock excludes concurrent local writers (`src/locks.ts:72-163`) but cannot exclude independent AO actors. An independent auditor needs provider-sourced evidence plus state/audit byte hashes and must label any missing or divergent link unresolved; `docs/MISSION_CONTROL_LIVING_SOP.md:19,37` notes that hashes are not an atomic snapshot.

## 5. Fencing and retirement semantics

| Term | What it means | What it cannot prove alone |
| --- | --- | --- |
| Controller STOP | Local policy blocks controller decisions; current default is active (`src/state.ts:31-47`, `src/mergePolicy.ts:123-124`). | AO queue drained or worker stopped. |
| Controller-local cancellation | Marks or abandons a local plan/attempt. | A submitted message was removed or will not execute. |
| AO delivery retirement | Provider durably records that a dispatch can never become executable again, with authenticated dispatch-ID evidence. | Already running work has stopped unless separately stated. |
| Queued-message cancellation | Removes or tombstones a queued item at all queue replicas/consumers. | A consumer that already dequeued it will honor STOP without a pre-spawn fence. |
| Worker execution fencing | Gate rejects stale epoch, grant, or session generation at worker creation and relevant effects. | Previously completed side effects can be undone. |
| Grant revocation | Trusted authority invalidates a grant and advances a durable epoch. B3A currently records only local, unverified-initiator revocation (`src/authorization.ts:207-239`). | AO has observed it or canceled queued work. |
| Session termination | Ends a particular live session/generation. | Another session or late message cannot create a new worker. |

The required STOP sequence is: authenticate STOP authority; persist a higher provider fence; stop accepting lower-epoch dispatches; retire or tombstone queued dispatches; make all consumers/worker-start gates observe that fence; return a durable barrier receipt; then reconcile dispatch IDs. If any step or acknowledgment is uncertain, the scope stays fenced and all related dispatches remain quarantined. The unresolved historical delivery is excluded from protocol migration and remains unresolved.

## 6. Failure-mode matrix

| Scenario | Required fail-closed response |
| --- | --- |
| Lost dispatch acknowledgment | Retain the original dispatch ID/digest as `UNCERTAIN`; block new identities and effects; use authenticated ID lookup. No new ID or blind resend. |
| Accepted but client disconnects | Treat response as unknown locally until lookup proves the durable acceptance and current fence state; do not infer rejection from disconnect. |
| Duplicate dispatch | Same ID and same envelope returns one provider record, never another worker; changed digest, target, generation, grant, or epoch rejects and raises incident evidence. |
| Delayed delivery after STOP | Provider rejects at queue admission or pre-spawn epoch gate; preserve retirement/barrier receipt. Without verified fence propagation, keep STOP and quarantine. |
| Restart after uncertain delivery | Reload ledger, audit, and provider epoch under ownership; query exact dispatch ID; block until complete authenticated history reconciles. Missing local or provider history is unresolved. |
| Stale worker session | Reject mismatched target/session generation before enqueue and before spawn; do not rebind old dispatch to a new generation. |
| Expired grant | Trusted clock check rejects admission and pre-spawn execution; persist authenticated rejection; never extend or refresh the same instruction implicitly. |
| Revoked grant | Advance durable provider fence and reject unstarted work; running work needs separate effect fencing/termination evidence. Local B3A revocation alone cannot clear the dispatch. |
| Conflicting fencing epoch | Reject lower or nonmonotonic epochs, freeze target, compare authenticated barrier and dispatch history; never choose the convenient value from controller state. |
| Malicious or malformed provider receipt | Reject unverifiable signature/channel, unknown schema, bad bindings, replay, conflicting sequence, or impossible transition; quarantine and preserve raw evidence for independent review. |
| Concurrent assignment attempts | Serialize local intent under controller lock, then require provider atomic ID and target/generation exclusion; a race or conflicting acceptance freezes the issue/branch. |
| Controller state/audit divergence | Treat provider effect and local history as uncertain; preserve both files and hashes, stop effects, reconcile from independent provider evidence. Do not fill gaps with synthetic receipts or delete evidence. |

## 7. Proposed implementation stages and acceptance criteria

These are future, separately reviewed stages. None authorizes a live call in this phase.

1. **Protocol evidence gate.** Obtain a versioned AO provider contract and source/maintainer evidence for every primitive in section 3, including every ingress path, retention, durability, and atomic fence ordering. **Accept when:** independent reviewers can trace each guarantee to AO implementation and a testable contract. **No contract:** stop here; consider AO changes before controller integration.
2. **Pure contract and verifier.** Define minimal envelope/receipt/lookup/retirement schemas and pure validation; reuse `DispatchRecord`, canonical digest, `AuthorizationRecord`, and quarantine rules. **Accept when:** malformed, forged, replayed, conflicting, stale-generation, and stale-epoch fixtures all deny; no production path becomes executable.
3. **Durable ledger and recovery design.** Specify fsync/transaction or equivalent durable store, evidence references, migration, and state/audit reconciliation. Preserve v4 uncertain/fixture records without promoting them. **Accept when:** crash-point and power-loss model tests prove no unrecorded handoff, duplicate ID, or false terminal state; divergence remains quarantined.
4. **Trusted issuer and execution gate.** Implement authenticated grants, revocation, one-use consumption, exact scope/session generation, provider-side STOP epoch, and mandatory pre-spawn check across all AO ingress. **Accept when:** adversarial queue delay, bypass-path, stale-worker, concurrent grant-use, and restart tests prove zero post-barrier new workers.
5. **Retirement, lookup, and independent evidence.** Add provider-authenticated ID lookup and durable retirement/barrier receipts, plus independent audit export. **Accept when:** accepted/disconnected, lost acknowledgment, duplicate, cancellation race, and contradictory receipt tests reconcile without replay or inferred retirement.
6. **Isolated integration review before Issue #13.** In a separately authorized environment, demonstrate end-to-end behavior and independently review provider source, threat model, operational recovery, and exact version pinning. **Accept when:** all gates above pass and human reviewers explicitly authorize a narrowly scoped live pilot. This assessment does not perform that pilot.

Existing relevant tests document local contracts: `src/__tests__/dispatch.test.ts`, `authorization.test.ts`, `assignment.test.ts`, `assignment.regression.test.ts`, `recovery.test.ts`, `state.test.ts`, `mergePolicy.test.ts`, and `reviewEvidence.test.ts`. A future isolated conformance suite must verify the actual provider binary/version under separate authorization. No AO tests or calls are part of this assessment.

## 9. Remaining blockers to live Issue #13

No confirmed AO dispatch/receipt/lookup/retirement protocol; no trusted issuer or execution-boundary grant verifier; no AO-side monotonic STOP and pre-spawn gate; no proven all-ingress coverage; no independent provider audit; no power-loss durability/atomicity design for local ledger and audit; no authoritative reconciliation of uncertain delivery; and no isolated end-to-end evidence or independent approval. The native review and merge policies do not close these assignment gaps. `issue12-phase2h-supervised-assignment` remains unresolved.

## 10. Explicit no-go criteria

Live AO assignment, retry, or Issue #13 demonstration is **no-go** if any of the following holds: a protocol primitive is undocumented or merely inferred from CLI/session behavior; a receipt is unauthenticated or not bound to exact ID/digest/target/generation/epoch; dispatch-ID lookup cannot conclusively cover delayed delivery; STOP lacks a durable provider barrier and pre-spawn fence on every ingress; grant issuance, revocation, or single use is caller-controlled; state/audit/provider histories diverge or are missing; crash/restart can replay an effect; a historical uncertain delivery would be altered; or independent review has not approved the implementation and evidence. Keep the current default-deny gate in place until all criteria are cleared in a separately authorized phase.
