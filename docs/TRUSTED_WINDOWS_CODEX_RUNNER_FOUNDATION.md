# Trusted Windows Codex runner foundation (S2B-1)

**Status:** contracts, lexical checks, and a pure preflight assessor only. No worker launcher, trusted provider, verifier, credential issuer, production authorization gate, or persisted worker state exists. Production execution remains disabled. The historical `issue12-phase2h-supervised-assignment` remains unresolved.

## Threat model and boundaries

A worker, its prompt, tools, children, output, logs, and claimed receipts are untrusted. It may attempt filesystem escape, credential access, network exfiltration, descendant survival, path substitution, forged readiness, or delayed execution after STOP. A caller may fabricate every TypeScript object in this phase. Controller-local observations cannot authenticate an external effect.

The Mission Control controller plans and requests work but must have no direct worker creation authority. A future trusted runner supervisor is the sole process creation and fencing authority. The worker process and every descendant are untrusted. A dedicated worker filesystem is writable only by its worker identity and trusted supervisor. Credentials and configuration are issued outside the worker filesystem and never inherited from the controller. GitHub integration is a separate trusted boundary with narrowly scoped credentials; the controller and worker do not receive a GitHub write token. Durable execution state belongs to the trusted supervisor and is bound to the existing B2 dispatch identity, rather than a parallel dispatch ledger. STOP and fencing must be enforced by that supervisor at the launch and effect boundaries. Worker-owned output remains untrusted until an independent verifier checks exact identity, provenance, digest, generation, epoch, and containment evidence. An AI prompt is not an enforcement boundary.

## Selected minimum Windows architecture

Use a dedicated low-privilege Windows identity per worker, provisioned by an administrator-controlled service. Deny that identity access to controller state, other workspaces, credentials, and GitHub writer material with NTFS ACLs. A trusted native Windows supervisor should create a restricted token, create the worker suspended, assign it to a Job Object before resume, disallow breakaway, and enforce process, memory, CPU, and runtime limits. It must track creation time plus PID and Job identity, descendants, and termination. A Job Object manages lifetime and some limits; it does not provide filesystem or network isolation.

Provision network denial or a narrowly scoped allowlist through an administrator-controlled Windows Filtering Platform policy or equivalent independently verified OS control tied to the worker identity and descendants. Do not infer network restriction from a worker prompt, Node configuration, or Job Object. The trusted supervisor constructs a minimal environment and allowlisted inherited handles, pins and hashes the executable from a trusted handle, and excludes controller profile, package manager, Git, cloud, proxy, and GitHub secrets. No elevated fallback is automatic. A separate read-only Tester/Reviewer identity and filesystem are required in later phases.

Node.js can validate data shapes, compare lexical paths, hash bytes it can access, plan admission, and interpret receipts. Node.js alone cannot prove ACL isolation, restricted token identity, non-bypassable network policy, safe descendant containment, live handle identity, or an atomic STOP barrier. Native Windows functionality is required for tokens, jobs, handle inspection, process creation ordering, and reliable termination. Administrator-controlled provisioning is required for identities, ACLs, and network policy. None of those controls is verifiably available in this development environment; no security experiment or ACL change was performed. AppContainer or a dedicated VM could provide stronger isolation, but each needs its own provisioning and conformance evidence; neither is assumed here.

## Filesystem model

`assessWindowsPath` and `assessWindowsFilesystemIdentity` reject relative, UNC, device, traversal, drive-root, reserved-name, alternate-data-stream, separator, case-binding, and lexical escape forms. The latter also checks claimed drive binding, canonical path consistency, and component reparse status. Its volume and file identifiers are **claims**. A future native verifier must obtain canonical final paths, volume serials and file IDs from open OS handles, reject or safely resolve every junction, symbolic link, mount point, and reparse point, and compare handle identities with the provisioned root. All open/create/rename operations need containment under protected directory handles and ACLs. A prior check of a path string cannot prevent a time-of-check/time-of-use replacement. If handle identity, volume, or component status is unavailable, deny readiness.

## Evidence, process supervision, and recovery

`TrustedWindowsEnforcementProvider` names nine narrow inspection functions. There is no adapter or process-launch method. `assessTrustedRunnerPreflight` validates S2A identity, capabilities, and fence against B3B envelope bindings and checks that each control has one scoped claim. It reports separate structural validity and local claim readiness. Its `independentlyAuthenticated`, `productionAuthorized`, and `executable` values are always false. A `TRUSTED_COMPONENT` label, evidence reference, fixture, or mock cannot promote a claim. S2B-2 needs an out-of-band trusted verifier with authenticated receipts and an atomic authorization gate; it must not simply add a boolean to this assessor.

A future launch receipt must bind worker execution ID, B2 dispatch ID and payload digest, repository, generation, fencing epoch, supervisor identity, OS process identity with creation time, Job Object identity, worker identity, workspace handle identity, executable hash, launch acknowledgment, and durable sequence. Completion requires authenticated process exit **and** verified containment or termination of all descendants, credential fencing, bounded external effects, and a durable terminal receipt. Exit code or missing PID alone cannot prove safe completion or retirement. Unknown ownership, lost acknowledgment, provider restart, or contradictory receipts remain uncertain and cannot be retried automatically.

## STOP race and crash contract

Before a future launch, the trusted supervisor must: (1) validate S1 admission; (2) verify current authorization independently; (3) acquire an exclusive start reservation; (4) revalidate STOP and epoch while holding a synchronization barrier shared with STOP activation; (5) verify isolation readiness; (6) bind execution identity and resource boundaries; (7) durably record launch intent; (8) start only through the trusted runner; (9) record authenticated launch acknowledgment; and (10) supervise all descendants and durably record outcomes. STOP must acquire the same barrier, advance a monotonic durable epoch, block new starts, fence credentials and external effects, and handle running descendants. A check followed by unprotected process creation is insufficient. Controller-local STOP cannot independently stop a detached external worker.

Every crash gap between these steps requires a durable phase marker and an independent lookup of launch, process tree, fence, and external-effect truth. A crash before intent may be safely abandoned only with proof that no launch was possible; a crash after intent or process creation is uncertain until authenticated non-start or full containment evidence is obtained. The future state format and durability protocol require review before implementation. S2B-1 writes no execution state.

## Integration and no-go

S1 remains a planning gate, S2A identity and fence remain structural, B3A production authorization remains denied, B3B receipts remain non-authoritative, B1 AO assignment remains denied, and B2 uncertain dispatches remain quarantined. S2B-2 needs a reviewed native supervisor, administrator-provisioned identities/ACL/network rules, tested executable and handle verification, a trusted issuer/verifier, atomic authorization and STOP barrier, crash-safe state migration, authenticated receipts, recovery tests, and independent source review. No live worker operation is permitted while any of these are absent, while the historical AO delivery is unresolved, or before a separately approved pilot. No existing AO installation is used to test this design.
