# Provider independent execution protocol contracts (Issue #23, B3B-3)

This document describes pure schema version **1** in `tools/mission-control/src/executionProtocol.ts`. It defines claims and deterministic checks only. It sends no instructions, changes no dispatch lifecycle, and provides no live execution mode. The historical `issue12-phase2h-supervised-assignment` delivery remains unresolved.

## Envelope and identity

The strict envelope contains protocol version, UUID dispatch ID, B2 operation key, repository owner/name, issue number, target ID, branch and optional worktree ID, agent role, positive target/session generation, authorization action scope, lowercase SHA-256 digest of B2 canonical JSON, digest algorithm identifier, grant ID, UTC issuance and expiry, nonnegative fencing epoch, and correlation ID. Unknown fields, unsupported versions, malformed IDs, missing bindings, noncanonical timestamps, and invalid time ranges fail parsing. It contains no executable instruction or secret. `matchesCanonicalPayload` recomputes the existing B2 digest over a supplied JSON value; the provider must bind the actual executable bytes to that digest before execution. The envelope is a proposed contract, not an authorization grant or transport message.

B2's persisted dispatch ledger remains the sole local identity record. `matchesDispatchRecord` checks the envelope against it; `assessEnvelopeIdentities` compares every immutable envelope binding for a reused dispatch ID in a proposed batch. Identical bindings are duplicate IDs; any changed binding is a conflict. Neither function writes state or releases an uncertain ID.

## Receipt claims and trust boundary

A receipt claim names a version, exact dispatch ID and payload digest, provider ID, repository, issue and target, generation, grant, epoch, durable event sequence, decision, timestamp, evidence reference, and authentication metadata. Decisions are `ACCEPTED`, `REJECTED`, `EXECUTION_STARTED`, `COMPLETED`, `RETIRED`, and `UNKNOWN`. The parser validates shape. `assessReceipt` checks binding and historical time consistency, including that acceptance and execution start are claimed before grant expiry. It can analyze completion or retirement claims after the envelope expires. `assessFence` separately checks whether a grant is currently valid for new execution and rejects expired grants. Local timestamps are consistency checks, not authenticated proof. **These functions operate entirely on caller supplied data.** Even a matching claim with a signature method, key ID, and proof reference has `authoritative: false`; those fields are untrusted strings. No environment variable, fixture, adapter response, local audit entry, or JSON field can change that result.

There is deliberately no production receipt verifier or trusted issuer implementation. A later separately reviewed verifier must independently obtain and authenticate provider identity, cryptographic proof or authenticated channel, key rotation and revocation, provider event history, durable sequence, retention, and exact binding. Only that separate boundary could produce authoritative evidence. A transport implementation must not treat this module's matching result as admission or execution permission.

## Lifecycle, fencing, and recovery

`assessReceiptHistory` returns `claimedOutcome` with `authoritative: false`; even a structurally matching terminal claim is not a verified provider outcome. A `RETIRED` history requires a supplied later fencing barrier bound to the exact dispatch, scope, generation, and barrier receipt reference. Without it, the claim remains `UNCERTAIN`. Historical completion and retirement may be analyzed after the envelope expires, while `assessFence` still rejects an expired grant for new execution. Neither receipt timestamps nor the local analysis clock authenticate a provider event.

Claim history permits `ACCEPTED → EXECUTION_STARTED → COMPLETED`, `ACCEPTED → RETIRED`, `EXECUTION_STARTED → RETIRED`, or an initial `REJECTED`. `UNKNOWN` is unresolved. Missing initial decision, replayed/nonincreasing sequence, time inversion, provider change, duplicate completion, and contradictory terminal outcomes yield `UNCERTAIN`. The classifier never mutates B2 state and never makes its outcome authoritative. A `NOT_FOUND` lookup claim remains uncertain even if its claimed coverage is complete; permanent rejection would require independently verified complete coverage and exclusion of delayed delivery.

The fencing snapshot names scope, current epoch, generation, barrier receipt ID, and durable evidence reference. Pure predicates reject stale or conflicting epochs, stale generations, expired grants, future issuance, wrong scopes, and retirement claims lacking a later barrier or matching receipt reference. These are checks over claims only. They cannot stop an AO queue consumer or prevent worker creation. An actual provider must durably order STOP and retirement against all admission, dequeue, restart, and pre-spawn paths, with atomic current epoch, generation, grant, and authorization checks. Retirement of queued work does not prove termination of already running work. Unknown or ambiguous outcomes stay quarantined; this module never retries, redispatches, reuses an uncertain identity, or clears B2 uncertainty.

## Roles and action permission

Roles are `ORCHESTRATOR`, `BUILDER`, `TESTER`, `REVIEWER`, `CORRECTOR`, and `MERGER`. They classify intended work. The separate action scope uses B3A's `ASSIGNMENT`, `REVIEW`, `CORRECTION`, `MERGE`, and `CLOSURE`. `roleMayRequestAction` is a narrow compatibility check, not a permission decision. A Builder cannot request Merge through this contract, a Reviewer cannot request Correction, and a Tester cannot request approval. A Merger label does not bypass GitHub protection or confer a trusted grant. B3A's production permission verifier remains default deny.

## Live execution no-go and integration dependencies

Live execution remains prohibited until a provider independently demonstrates immutable ID binding and idempotency, durable authenticated receipts and complete exact-ID lookup, trusted issuer and actor verification, atomic one-use grant consumption, all-ingress generation and epoch checks, durable STOP barriers and retirement, ordered event history, crash recovery, and independent audit evidence. Supervised and autonomous modes both need those provider controls, a separately reviewed verifier, local ledger/evidence migration rules, and independent review before integration. AO is one possible provider; current AO evidence does not establish these capabilities. B1's live default-deny gate, B2's uncertainty quarantine, and B3A's fail-closed authorization remain in force.
