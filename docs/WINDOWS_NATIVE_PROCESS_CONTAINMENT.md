# Windows native process containment prototype (S2B-2B1)

**Status:** source skeleton and portable deterministic tests. No native binary was compiled or run; no fixture process was started. Containment has **not** been demonstrated. Production execution remains disabled. `issue12-phase2h-supervised-assignment` remains unresolved.

## Technology decision

The selected narrow approach is a small C++ helper using the Windows SDK. Direct Win32 calls make handle lifetime, `GetLastError`, process creation flags, and token verification reviewable together. A Node native addon would add ABI and packaging complexity and still require native code; `koffi` already exists in the toolchain but does not make safe process creation, handle ownership, or crash supervision automatic. No new dependency was installed. Neither `cl`, `clang-cl`, `g++`, nor `cmake` was found on PATH in the authorized workspace; a Windows SDK include directory exists. This blocks compiling and native runtime experiments in this phase. The source is therefore deliberately unlinked and has no `main`, npm script, or dispatch import.

`tools/mission-control/native/disposable_job_probe.cpp` implements RAII ownership for a Job Object created with default non-inheritable handle attributes by `CreateJobObjectW`. It applies `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and an active process limit of one with `SetInformationJobObject`, then reads the limits back with `QueryInformationJobObject`. It contains dormant functions for `AssignProcessToJobObject`, `IsProcessInJob`, and `TerminateJobObject`; `CloseHandle` releases the owner handle. Creation, setup, query, assignment, and termination request failures record an API name and `GetLastError` code. `CloseHandle` failures are not checked or reported by this skeleton and require further native implementation and runtime testing. No current call site creates or assigns a process. Configuring a Job Object is distinct from demonstrating that a process was contained. The active process limit is a source setting, not a runtime-validated limit. No memory, CPU, wall-clock, output, or network limit is enforced.

## Job and process guarantees

When compiled and independently tested, kill-on-close should request termination of processes in the job when the last job handle closes. A duplicated or inherited owner handle could defeat that lifetime assumption. The source uses default non-inheritable security attributes, deletes copy operations, and closes the handle in its destructor; these source properties are not a tested handle-inheritance guarantee. A future child creation path must also use an explicit empty or tightly bounded handle list via `STARTUPINFOEX` and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, verify handle flags, and retain only supervisor ownership. `TerminateJobObject` success is a request, not observed exit. `QueryInformationJobObject` and process handles must establish descendants and final exit; final process exit verification still requires native implementation and runtime testing. A missing PID or vanished supervisor is uncertain. Nested Job Object assignment may fail under host job restrictions; no breakaway fallback is allowed.

Job Objects manage process membership and selected resource limits. Job membership is distinct from restricted-token security. Job Objects do not isolate files, network, credentials, or the user's identity. The current implementation has no filesystem, network, credential, or worker identity enforcement.

## Process creation race and identity

There is no child creation code. A future disposable fixture must be a fixed, repository-owned binary built in this workspace, with no supplied executable path, arguments, shell, PowerShell, Codex, or AO command. It must perform no network, credential, external file, or other-process operations. Merely creating a process suspended and assigning its job afterward is insufficient without a complete fail-closed path for every API error, thread resume, inherited handle, and supervisor crash. Creation-time job assignment through `PROC_THREAD_ATTRIBUTE_JOB_LIST` on a supported Windows version is the preferred candidate; availability and exact semantics must be verified before a runtime experiment. If unavailable or incompatible with a nested host job, no real child should start. No Windows version support is claimed by the uncompiled source.

The restricted identity boundary is **UNAVAILABLE**. A later review must use `CreateRestrictedToken`, remove privileges, constrain SIDs/groups, set and verify integrity level, create the fixture with that token, query its effective token, and test effective filesystem access. `CreateProcessAsUserW` or another appropriate restricted-token creation path may require privileges unavailable in this sandbox. The interactive user's unrestricted token is not isolation evidence. No account or ACL is changed. Token isolation and Job containment are separate controls; nested job conditions must be handled without breakaway.

## Lifecycle, STOP, and evidence

`nativeContainmentPrototype.ts` models CREATED, CONTAINED, RUNNING, EXITED, TERMINATION_REQUESTED, TERMINATED, and CONTAINMENT_UNCERTAIN. It rejects malformed stage, event, observation, STOP gate, and receipt tracker inputs; accessor properties and unexpected nested error fields fail closed. It also rejects invalid process identity, missing Job ownership/query, failed setup, unsupported ordering, stale generation, STOP before setup or start, and replayed receipt IDs. Missing termination observation yields uncertainty and retry remains false. These are checks over **caller-supplied claims**. They neither perform native calls nor authenticate a receipt. Every result has `authenticity: UNVERIFIED`, `productionAuthorized: false`, and `executable: false`, including claimed success.

A future trusted supervisor must serialize STOP activation and disposable launch under one lock or equivalent barrier. Under that barrier it must validate the current generation, reserve the start, establish containment before executable instructions run, and only then release the barrier. STOP must advance a monotonic generation and prevent new starts while the same barrier is held. On setup failure it must close thread/process handles, terminate any suspended child, close the Job owner handle, and verify exit before reporting a terminal state. Supervisor crash, failed query, or incomplete exit evidence remains uncertain and prohibits retry. None of this is an implemented runtime guarantee here. STOP does not retire or reconcile AO delivery.

The typed observation names PID, Job ownership/query, worker identity/restrictions, termination observation, timestamp, generation, and Win32 API error. It is labeled `LOCAL_NATIVE_CLAIM`; no independently authenticated native verifier exists. The model rejects a forged authenticated source label and locally tracked replay, but local tracking is not durable anti-replay protection. A future authenticated receipt must bind supervisor identity, process creation time, job identity, generation, sequence, and independently checked process-tree exit before it can support a trusted decision.

## Testing and portability

Default `npm test` and controller tests run only pure TypeScript fixtures and are portable to GitHub-hosted Windows and non-Windows runners. They exercise valid and failed claims, ordering, STOP, stale generation, replay, malformed results, missing evidence, unsupported runtime/nested jobs, token failure, and constant denial of authority. They do not test OS containment, handle inheritance, kill-on-close, or real cleanup. There is no native opt-in command yet, because no safe fixed fixture creation path or compiler was available. Do not interpret mock outcomes as OS evidence.

## Production no-go

No production worker may run until a reviewed native build and fixed fixture demonstrate atomic containment before execution, restricted token and effective ACL verification, handle inheritance control, nested job behavior, complete process-tree termination, durable STOP ordering, authenticated receipts, and independent review. S1 admission, S2A contracts, S2B-1 preflight, and S2B-2A read-only inspection remain non-executable. Live AO assignment remains blocked; no AO state was accessed or changed.
