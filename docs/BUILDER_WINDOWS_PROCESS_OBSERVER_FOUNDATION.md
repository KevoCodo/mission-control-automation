# Gate 2B Windows process observer foundation

## Scope

`processObservationEvidence.ts` defines a portable version 1 record and a pure assessor. It reads caller-supplied data only. It starts no ETW session, reads no live trace, launches no process, and grants no execution authority. Experiment 00 and all later experiments remain **NO-GO**.

The assessor returns `MALFORMED` for records outside the exact own-data schema, `REJECTED` for inconsistent or incomplete records, and `UNVERIFIED` for a locally consistent record. Every result has `noChild: UNVERIFIED`, `independentlyAuthenticated: false`, and `executionAuthorized: false`. A missing child event is never proof that no child ran. A caller's SHA-256 values, coverage claim, cleanup claim, and `rawEventId` values are data, not independently verified evidence.

## Version 1 record

The record identifies the session, collector and provider claims, configuration and raw trace digests, lifecycle and interruption count. It specifies observation, launch, harness exit, and post-exit boundaries; harness and parent identities; process start/end events with collector-assigned contiguous sequence, timestamp, raw-event identifier, PID, creation identity, and full parent identity; three loss counters; and cleanup time and outstanding process identities. Each creation ID must name one PID throughout the record, including reserved identities, event processes, event parents, and cleanup references. Repeated references to that same PID and creation ID are allowed; aliasing the creation ID under another PID is rejected before it can mask an ancestry cycle. The harness parent is a reserved, pre-existing root: it cannot be started as a descendant or have its PID or creation identity reused by an observed process. The harness must have a distinct PID and creation identity from that root. Ancestry cycles are rejected. PID reuse among newly observed descendants is locally consistent only when creation identities differ and the prior process has an observed end; those observations remain unauthenticated. Reuse of the reserved parent's PID is always unresolved in this phase, because its retirement cannot be proven here. A process start without a known active parent, duplicate start, missing exit, sequence gap, clock contradiction, unknown or nonzero loss, observer interruption, incomplete window, or incomplete cleanup is rejected.

The parser accepts only exact, dense, ordinary JavaScript data objects and arrays. It inspects property descriptors to avoid executing getters. Accessors, symbols, extra fields, sparse arrays, and foreign prototypes are malformed. Throwing Proxy traps are caught; an arbitrary Proxy is **not** a safe input format and cannot be authenticated by this parser. A future trusted collector must materialize records across a controlled serialization boundary before assessment.

## Future Windows collector mapping

A separately reviewed Windows Kernel Process ETW collector would need to map actual process start and end payloads to `PROCESS_START`/`PROCESS_END`, PID and parent PID, and an independently supported creation identity. If the source payload cannot guarantee stable, globally unique process-instance identities, the collector must derive and verify them before producing this contract; PID alone cannot supply a creation ID. It must verify provider identity and configuration, record its session lifecycle, observation boundaries, relevant loss counters and collection failures, and retain raw trace evidence bound to the recorded digest. The portable `sequence` is a collector export sequence; it must not be represented as an ETW-provided global sequence without a verified source for that guarantee. `rawEventId` must identify the underlying event in retained evidence. Timestamps need a documented clock domain and conversion that preserves ordering.

PID and parent PID alone do not authenticate process identity across reuse. The collector must independently resolve parent creation identities and show that its filtering and event capture cover every relevant child, including short-lived children, before a no-child result could be considered. It must also demonstrate loss and restart detection, the required prelaunch and postexit windows, privileges and host policy impact, and independently observed cleanup. A provider configuration string or zero caller-supplied loss counters cannot establish capture completeness. No Windows collector or these guarantees exists in this milestone. Linux and macOS are not assumed to offer equivalent evidence.
