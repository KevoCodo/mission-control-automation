# Gate 2B: independent Windows runtime containment experiment plan

**Status: PLAN ONLY — NO RUNTIME AUTHORIZATION.** This document specifies disposable experiments; it records no runtime result. No build, fixture, harness, worker, Codex process, controller CLI, AO action, Operis action, ACL change, network-policy change, or elevated action was performed for this plan. Production execution and all default-deny gates remain disabled.

## Source baseline and decision rule

The actual Gate 2A commit is `c14b9af942ff90816ff7b88736216cda4156f733` (`feat(controller): harden Windows worker isolation claims`), present at `HEAD` when this plan was written. Its diff includes `docs/BUILDER_TRUSTED_WINDOWS_GATE2A.md`, changes to the native probe and TypeScript assessors, and fixture tests. A pre-existing modification to `tools/mission-control/src/__tests__/__snapshots__/reportGolden.test.ts.snap` is outside this plan and was left untouched. Before any future experiment, record the then-current commit and diff against this baseline; a changed native source or build script requires fresh source review. The prior documentation reports a successful native compilation, **not** a run or containment result.

Each experiment has its own GO/NO-GO decision signed by an independent Windows security reviewer. GO means its prerequisites and evidence collection are ready for a separately authorized run; it does not mean the control passed. A passing result requires all expected observations and independent evidence. A fail, missing observation, or ambiguous cleanup is NO-GO for that experiment and all dependent experiments. Never turn a local harness success string into production readiness.

## Permitted source, build, and executable identity

The only native source permitted for the **initial** source-supported runs is `disposable_job_probe.cpp`, `disposable_job_harness.cpp`, `disposable_fixture.cpp`, and `build-disposable.ps1` from `tools/mission-control/native` at the reviewed commit. `disposable_job_probe.cpp` is included by the harness, not built into a third executable. The only permitted executable outputs are `disposable_job_harness.exe` and `disposable_fixture.exe`. The only permitted harness argument is `--run-fixed-fixture`. No Codex executable, shell payload, worker, AO CLI, generic command selector, or external target binary is permitted. The TypeScript `nativeContainmentPrototype.ts` and `windowsFilesystemPreflight.ts` are claim assessors, not runtime test authorities.

For a separately authorized build, the test custodian copies the four reviewed files to the exact `src\tools\mission-control\native` path above. Record owner SID, effective access for the custodian, compiler identity, test identity, and other local principals on the files and every ancestor. Independently enforce source-file and ancestor protection against write, delete, rename, or replacement throughout compilation; grant the builder write access only to the distinct `build` output subtree. A read-only file attribute alone is insufficient, and no protection is assumed until the host's effective controls are verified. Record each staged file's path, volume/file ID, size and SHA-256; compare its bytes with the reviewed Git blob before the build. Rehash and recheck file IDs for **every** staged source file, including the script and included probe, after each compilation, and require exact agreement with its pre-build value. An input change, inaccessible file identity, or unverifiable replacement protection is NO-GO; discard the outputs as untrusted.

Resolve `cl.exe` and the linker actually invoked by `cl /link` within the same `vcvars64.bat` environment used for the build, not from a separate shell or an assumed installation path. Record their resolved canonical paths, file IDs, SHA-256, version/signature and observed process-image identities. Record the actual `cmd.exe` process image and the canonical path, file ID, SHA-256 and contents of the `vcvars64.bat` script it executed; a batch file is an input, not a process image. Record the canonical paths, file IDs and SHA-256 of the relevant Windows SDK headers and libraries actually selected by include/lib search (at minimum the directly included Windows headers and linked system libraries); capture include resolution, library resolution and transitive inputs needed to explain the build. Verify those inputs and their ancestors are independently protected from replacement during compilation, and recheck their identities afterward. A version banner, `PATH` entry, or pre-build hash alone does not establish which image or input the build used. If process-image or dependency resolution cannot be tied to the observed build, NO-GO.

Run the script from the protected source copy first without the runtime switch. Build with `-EnableRuntimeExperiment` only after experiment 00 passes and a separate runtime-build authorization is granted; distinguish the default-disabled and enabled harness by separate hashes and manifests. Record the exact compiler/linker invocations, response files, working directories, command-line switches, include/lib search order, relevant environment variables and `vcvars64.bat` effects, tool and SDK input identities, build log, PE metadata, output sizes, Authenticode status if any, and SHA-256 of both outputs in a reproducible build manifest. Capture the actual resolved tool processes with a reviewer-approved observation method; verify its coverage before relying on it. Mismatched source hashes, unresolved toolchain inputs, incomplete manifest, or unverified provenance/replacement protection are NO-GO. A successful build grants no run permission.

The reviewer validates each pair, then stages the default-disabled pair in `run\sealed\default-deny` and the enabled pair in `run\sealed\baseline`, with independently verified effective controls preventing the test identity from writing, deleting, renaming, or replacing either file or an ancestor. Verify ordinary non-reparse path components and final file IDs/volume IDs through open handles. Record hashes of the **staged** files, not just compiler outputs; independently rehash and compare file IDs immediately before and after every run. Protect the artifact manifest from the test identity. If the host cannot provide a protected staging directory and independent identity check, NO-GO. The present harness checks `GetFileAttributesW` and starts a sibling path; it does not hold a pinned executable handle or cryptographically bind the checked file to `CreateProcessW`. These measures reduce substitution risk but **cannot prove race-free executable identity**. A replacement/swap experiment requires reviewed new implementation and a separate GO decision.

## Independent observation gate for process ordering

Source inspection establishes only the intended control flow: Job-list attribute setup, `CreateProcessW`, `IsProcessInJob`, then conditional `ResumeThread`. Harness stdout, its Win32 result strings, later process enumeration, and a post-start membership snapshot cannot establish runtime API order or prove that no fixture instruction executed before containment. The independent reviewer must approve an observer **outside the harness and tested Job** before experiments 00–02. Candidate methods for review include externally controlled debugger/API-call observation of the harness and child, or an OS event trace combined with separately verified API-argument/result and thread-state observation. These are candidates only: no ETW provider, debugger, or tracing tool is presumed to emit the required fields or give sufficient ordering guarantees. Intrusive breakpoints or injected hooks must be assessed for changes to tested timing, creation flags, Job assignment or resume behavior; a method that meaningfully changes the behavior under test is NO-GO.

The observer design must document its exact provider/tool version and binary hash, required privileges, attachment/start sequence, process identity and creation time, loss/drop counters, clock source and calibration, timestamp resolution, event sequence semantics, and whether event delivery order equals operation order. Prefer an unelevated observer; a mechanism requiring elevation or host policy changes is NO-GO under this plan and needs a separate disposable-host authorization and plan revision. Preserve raw, unedited trace output plus a hashed, machine-readable event export that binds provider, event type, process/thread ID with creation time, Job identity, arguments, return value, event sequence, timestamp/clock domain and trace-loss status; an independently signed interpretation must cite those records. For 00, it must independently cover child creation attempts and confirmed absence of the fixture child across the bounded run and cleanup window; absence of an event alone is insufficient unless coverage and loss bounds are validated. For 01–02, it must independently bind the exact harness/child/Job identities and record the Job-list attribute and arguments, `CreateProcessW` flags/result and creation-time Job membership, `IsProcessInJob` arguments/result while the primary thread is suspended, and the first `ResumeThread` call/result or its absence. It must establish a defensible happens-before relation for these operations, using a verified event sequence or synchronized timestamps with adequate resolution and no unobserved gaps. If a candidate lacks an API argument, result, Job identity, suspended-state observation, or proven ordering semantics, it cannot support a PASS. Record the observer's privileges and ensure it does not confer rights on the fixture. Any observation method or privilege change requires separate review and authorization; no method is approved by this plan.

## Global STOP and authorization checkpoints

Stop the entire sequence immediately for unexpected process creation or behavior, an unknown PID/creation time, Job escape, breakaway, inherited or duplicated control handle, privilege escalation, successful or ambiguous out-of-workspace access, outbound network activity, executable replacement, missing/contradictory independent evidence, a cleanup timeout, or any surviving process/descendant. Do not retry or continue to the next row. Preserve artifacts and the disposable host state; an independent reviewer decides containment and cleanup before any resumption. Never inspect or manipulate live AO or Operis to resolve an uncertainty.

**Checkpoint A — plan/source:** independent reviewer confirms commit, exact source/binary allowlist, test-root separation and gaps above. This checkpoint authorizes no build or run. **Checkpoint B — build/staging:** explicit human authorization for disposable source copying, source/toolchain protection and provenance verification, default-disabled compilation, staging, controls confined to the test root, hash review and host observation setup. A separate build authorization is required for `-EnableRuntimeExperiment`. Build approval alone authorizes no execution. **Checkpoint C — each run:** explicit human authorization names the host, test root, identity, exact two hashes, experiment and branch, time window, independently reviewed observer, cleanup owner and stop operator. Record GO before running each row; a prior row's approval does not carry forward. Experiment 00 approval does not authorize enabled-harness experiments. **Checkpoint D — expanded controls:** separate explicit human authorization and revised source review are required for fault injection, new descendant/resource/file/network fixtures, restricted-SID or ACL provisioning, reparse/symlink creation, network policy or endpoint use, intentional harness interruption, watchdog deployment and rollback. Any action requiring administrator elevation or host security-policy change is outside this plan and needs a separately approved disposable-host procedure; no elevation or policy change is implied here. **Checkpoint E — acceptance:** independent reviewer signs each PASS/FAIL/INCONCLUSIVE and final cleanup, with no automatic promotion to production or an Operis pilot.

Job Object evidence can establish process membership, process-count/lifetime behavior, and selected resource limits on the tested host. It does **not** establish filesystem confinement, worker identity or effective NTFS permissions, network denial, executable pinning, authenticated STOP, or durable recovery. Those are separate controls with separate experiments and GO/NO-GO decisions. Until all required controls have independently passed on the intended host and an additional production gate authorizes integration, Mission Control remains planning-only and production execution remains denied.
