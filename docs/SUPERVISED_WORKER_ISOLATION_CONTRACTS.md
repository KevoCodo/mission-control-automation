# Supervised worker isolation contracts (S2A)

**Status:** pure, provider-independent contract assessment. No runner, provider adapter, process launch, trusted issuer, persistent worker state, network transport, or live AO execution is added. The historical `issue12-phase2h-supervised-assignment` dispatch remains unresolved.

## Identity and dispatch binding

`WorkerIdentity` version 1 binds a unique worker execution ID to the B3B `ExecutionEnvelope` dispatch ID, repository owner/name, issue, role, target ID, generation, branch, worktree ID, grant ID, fencing epoch, correlation ID, and exact issued/expiry times. It additionally names one absolute workspace root and the expected 40-character Git base commit. `parseWorkerIdentity` rejects missing, extra, malformed, expired, or conflicting fields, unsupported versions, and an envelope without a worktree ID. The envelope retains the B2 operation key and canonical payload digest; S2A does not create a second dispatch identity or ledger. Neither record authorizes execution. The base commit and workspace binding need independent verification against a future trusted checkout and filesystem handle.

## Isolation and capabilities

`WorkerCapabilities` defines one assigned workspace root with explicit read/write operations, a single absolute executable path and SHA-256 identity, denied or destination-allowlisted network access, an environment variable name allowlist, no or repository-scoped read-only GitHub access, and positive CPU, memory, process-count, runtime, and output limits. Credentials are never stored in this contract. The schema rejects wildcard executables, open network destinations, missing limits, and elevated GitHub mode. The only environment variable name accepted by S2A is `S2A_FIXTURE_MARKER`, once, for inert contract fixtures. Names affecting executable resolution, module loading, Git, credentials, home/profile paths, proxies, or shell behavior are rejected. This fixture allowlist is **not** a production security guarantee: a future runner must construct its environment independently from trusted policy. Builder and Corrector may request write scope only for their own assigned workspace. Tester and Reviewer are read-only in this phase; their roots and process identities must be independent of Builder. Role names confer no capabilities. A future privileged GitHub action needs a distinct, trusted action grant and a narrower operation contract.

`assessWindowsPath` rejects relative paths, dot segments, drive roots, UNC/device names, alternate data streams, mixed separators, reserved device names, trailing dots/spaces, case-binding mismatches, and lexical escapes. `assessFilesystemAccess` also demands component evidence because a path that looks contained may traverse a symlink, junction, mount, or reparse point. These are lexical checks, **not a security sandbox**. The `VERIFIED_NO_REPARSE` input is still a caller claim. Actual enforcement requires an OS sandbox, restrictive filesystem ACLs, safe handle-relative operations with reparse controls, canonical final-handle comparison, and containment checks at each open/create/rename. The runner must prevent time-of-check/time-of-use swaps and must ensure all descendants and tools inherit the same constraints.

## Lifecycle and evidence

The proposed stages are `PLANNED → ADMISSION_PENDING → AUTHORIZED → STARTING → RUNNING → RESULT_PENDING → COMPLETED | FAILED | UNCERTAIN | FENCED`. Pure `assessWorkerTransition` allows only declared edges and requires a bound event for each non-uncertain edge. Local intent can support planning and starting claims; external process observation can support an exit claim; authenticated provider evidence is required for a start or terminal claim; trusted execution authorization is required for authorization. A caller-supplied status, PID, exit code, audit line, or receipt shape does not establish completion, failure, retirement, or descendant containment. Every S2A result has `authoritative: false` and `executable: false`, even when its structure is contract-eligible. No lifecycle state is persisted.

## STOP, generations, and recovery

`assessWorkerFence` defaults to denial when STOP is active or unknown, a durable epoch or barrier reference is missing, a worker or dispatch generation differs, the grant is expired/revoked/conflicting, or the envelope epoch is stale. A newer durable fence makes a late start structurally ineligible. The barrier reference is not authenticated here; S2A makes no claim of OS-level STOP enforcement. A trusted future gate must atomically check the durable fence and grant immediately before process creation and before every relevant external effect, across all ingress paths.

`classifyWorkerRecovery` distinguishes never-attempted launch, lost acknowledgment, observed running process, exit without containment, termination without descendant proof, provider restart, stale generation, missing evidence, and contradictory evidence. Contradictory launch or containment observations are classified before a never-attempted claim. Malformed assessment inputs deny conservatively. Every classification has `retryEligible: false` and `retired: false`. A missing process/session cannot prove retirement, and a lost acknowledgment cannot be replayed. B2 uncertainty remains quarantined; no historical dispatch is altered or synthesized into a trusted receipt.

## S2B prerequisites and no-go conditions

A trusted Codex runner needs a pinned executable and narrowly specified invocation, real OS isolation and process-tree supervision, independent workspace and Git-base verification, constrained network and credentials, authenticated provider launch/result/retirement receipts, durable ordered audit and dispatch bindings, a trusted grant issuer and verifier with atomic single use and revocation, and a durable STOP barrier enforced at process creation and all effect paths. Crash recovery and exact-head Tester/Reviewer separation need isolated conformance tests. Local state, audit, and locks do not currently provide cross-process or power-loss atomicity. Prompt instructions are never a security boundary.

Supervised operation would require authenticated human approval for privileged steps. Autonomous operation needs separate policy and authority. Neither mode is enabled. Issue #23 supplies safety, fencing, and recovery requirements; Issue #13 remains a separate end-to-end demonstration goal with live AO criteria that S2A does not satisfy. Live execution is **no-go** while any issuer, sandbox, grant, barrier, all-ingress, descendant-containment, durable receipt, independent audit, or recovery guarantee is missing or unverified, while the historical AO delivery is unresolved, or before independent review approves a narrowly scoped next phase. B1 live AO denial, B2 uncertainty quarantine, B3A production permission denial, B3B receipt non-authority, and S1 admission-only behavior remain in force.
